## Server shape and public API surface (backend `v8.0.49`)

Single Go service (Gin). Entry `cmd/server/`; embeddable SDK entry `sdk/cliproxy/` with fluent `Builder` (`sdk/cliproxy/builder.go`).

Public inference routes, all behind `AuthMiddleware(s.accessManager)` (`internal/api/server_routes.go:60-113`):

- `GET /v1/models` (+ `/v1/models/*model` detail), `POST /v1/chat/completions`, `POST /v1/completions`
- `POST /v1/messages`, `POST /v1/messages/count_tokens`
- `POST /v1/responses`, `GET /v1/responses` (WebSocket), `POST /v1/responses/compact`
- `POST /v1/audio/speech`, images (`/v1/images/generations|edits`), video endpoints, `POST /v1/tts`
- `POST /v1/alpha/search`, `POST /v1/live` (+ sideband), `/v1/realtime*` family
- Gemini protocol: `GET /v1beta/models`, `POST /v1beta/interactions`, `POST /v1beta/models/*action`
- Codex direct aliases under `/backend-api/codex/*`
- `GET /healthz` (unauthenticated), `GET /management.html` (control panel; see below)

Client authentication is configured via `access.api-keys` (`config.example.yaml:118-123`) and enforced by a provider-registry access layer (`sdk/access/registry.go:11-17` `Provider` interface; `internal/access/config_access/provider.go:13-27` registers the config keys). Custom access providers can be added through `sdk/access.RegisterProvider` and `Builder.WithRequestAccessManager` (`sdk/cliproxy/builder.go:143-146`).

Management surface: `/v0/management/*` (`internal/api/server_management.go:28-201`) and `/v8/management/*` (`internal/api/server_management_v8.go:12-70`). Both require the management key (`management.secret-key`, plaintext auto-hashed to bcrypt at startup per `config.example.yaml:100-103`) via `Authorization: Bearer` or `X-Management-Key` (`internal/api/handlers/management/handler.go:324-358`). Remote (non-localhost) management additionally requires `management.allow-remote: true` (`handler.go` `AuthenticateManagementKey`), with 5-failure/30-minute per-IP ban. Management keys and client (`access`) keys are distinct stores; the plan's "separate inference and management keys" requirement maps directly onto this split.

Existing Tokligence dependency check: `quota.mjs` calls `/v0/management/auth-files` — this route exists at `v8.0.49` (`internal/api/server_management.go:180` → `ListAuthFiles`) and v0 remains supported per `docs/management-api-v8.md:4-6`, but the native dashboard does not use v0 except as a legacy-diagnostic probe (`src/services/api/legacyBackendProbe.ts`, "Diagnostic only").

## Extension points and lifecycle (the core evaluation)

Three extension mechanisms exist. All are in-process or plugin-boundary constructs; none is a sidecar.

### 1. Go SDK executors (in-process, compile-time)

`ProviderExecutor` interface: `Identifier/Execute/ExecuteStream/CountTokens/HttpRequest` (`sdk/cliproxy/executor/types.go` — the SDK `Request/Options/Response/StreamResult/StatusError` types define the executor contract; the reference doc example is `docs/sdk-advanced.md`, working example `examples/custom-provider/main.go`).

- Registration: `Manager.RegisterExecutor` (`sdk/cliproxy/auth/conductor_lifecycle.go:36-60`) keyed by `Identifier()`; an app builds its own binary via `cliproxy.NewBuilder().WithCoreAuthManager(core)` and registers custom executors before `Run` (example `examples/custom-provider/main.go:185-215`). **This means a custom provider requires building our own server binary from the SDK (`cmd/server` equivalent), not using the stock release binary.** The stock binary registers the built-in executors (claude, codex, antigravity, aistudio, vertex, kimi, xai, devin, meta, openai-compat) in `sdk/cliproxy/service_executors.go:290-330`.
- Protocol translation: `sdk/translator/registry.go:30-49` `Register(from, to, requestTransform, responseTransform)`; the executor receives already-translated payload plus `opts.OriginalRequest` (raw inbound bytes) and the `SourceFormat/ResponseFormat` (`sdk/cliproxy/executor/types.go:204-238`). The executor itself calls `sdktranslator.TranslateNonStream/…` (`internal/runtime/executor/openai_compat_executor.go:233`).

### 2. Dynamic-library plugins (runtime-loaded, cgo)

`plugins.enabled/dir` config (`config.example.yaml:1232-1236`); loader `internal/pluginhost/loader_unix.go` (dlopen-based `dynamicLibraryLoader`), host wrapper `sdk/pluginhost/host.go`. Plugin capability schema is `sdk/pluginapi/types.go` (`Plugin.Capabilities`): `AuthProvider` (parse/login/poll/refresh — the OAuth extension point, `types.go` `AuthProvider interface`), `Scheduler`, `ModelRouter`, `Executor` (`ProviderExecutor` at `sdk/pluginapi/types.go:733`), `RequestTranslator/RequestNormalizer/ResponseTranslator`, `RequestInterceptor` (before/after credential selection, `types.go:1175-1180`), `ResponseInterceptor`, `StreamChunkInterceptor`, `RequestLifecyclePlugin`, `ManagementAPI` (plugin-owned management routes under the host prefix), `QuotaProvider` (`types.go:1721-1731`), `UsagePlugin`, `CommandLinePlugin`. Plugins are third-party compiled libraries loaded into the server process; the plugin store (`internal/api/handlers/management/plugin_store.go`, `/v8/management/plugins/store`) can install them from a registry.

### 3. Configuration-level extension: `openai-compatibility` providers

No-code provider definition (`config.example.yaml:897-955`, struct `internal/config/config_types.go:963-1008`): name, base-url, api-key entries (per-key weight/proxy), model list with aliases, custom headers, per-provider `disable-cooling`, per-provider `request-retry`, per-provider `request-scoped-errors` classification rules, `support-prompt-cache-key`, `prefix`. Handled by the built-in `OpenAICompatExecutor` (`internal/runtime/executor/openai_compat_executor.go:50-60`, registered per provider at `sdk/cliproxy/service_executors.go:336-357`). If a plugin provides an `AuthProvider` for the same provider key, the executor is wrapped with `PluginRefreshCompatExecutor` so OAuth refresh is delegated to the plugin while request handling stays native (`service_executors.go:339-376`).

### Request path ordering (verified, `v8.0.49`)

Non-stream (`sdk/api/handlers/handlers_execution.go:47-127`) and stream (`sdk/api/handlers/handlers_stream.go:28+`):

1. Route handler (e.g. `openaiHandlers.ChatCompletions`) → `BaseAPIHandler.Execute*WithAuthManager`.
2. `applyModelRouter` (plugin `ModelRouter` may re-route to a plugin executor) — `handlers_execution.go` via `routeDecision`.
3. `providersForExecution` — model→provider resolution (exact model, aliases, prefixes).
4. `applyRequestInterceptorsBeforeAuth` — plugin request interceptors, **before** credential selection (plugin can reject/rewrite here — an enforcement point that runs on every request path including this one).
5. `AuthManager.Execute/ExecuteStream` (`sdk/cliproxy/auth/conductor_execution.go:123/240`): session enrichment (`cliproxysession.Enrich`), provider normalization, then the round loop: `executeMixedOnce` per round → selection (`Selector.Pick`, `sdk/cliproxy/auth/conductor.go:107-111`; plugin `Scheduler` may take over via `PickAuth`) → `RequestAfterAuthInterceptor` (second plugin interception point **after** credential selection, before executor translation) → executor `Execute/ExecuteStream` (physical network send inside executor).
6. On failure: `shouldRetryAfterErrorWithAttempted` decides next round from `request-retry`/`max-retry-credentials`/`max-retry-interval` and cooldown state; `MarkResult` (`sdk/cliproxy/auth/conductor_cooldown.go:889-903`) applies `ResultPolicy` **before** any quota mutation/persistence — the documented veto point.
7. Response path: `applyResponseInterceptors` (plugin response/stream-chunk interception) → downstream.

Count-tokens (`ExecuteCount`) follows the same rounds; results carry `SkipQuotaObservation: true` (`conductor_execution.go:883`) so counting traffic does not corrupt quota watermark observation.

Protocol translation vs history repair: translation happens in the executor layer (each executor translates via `sdk/translator` with `opts.OriginalRequest` preserved); "history repair" as a distinct named module does not exist under that name in `v8.0.49` — the nearest mechanisms are (a) per-executor request normalization (e.g. `sanitizeOpenAIResponsesReasoningEncryptedContent…`, `apply_patch` repair tests under `internal/runtime/executor/`), and (b) plugin `RequestNormalizer`/`ResponseBeforeTranslator`. **Unknown/verify-at-slice-time:** exact reasoning-signature repair behavior for Claude-style thinking blocks per provider is spread across executors (`internal/thinking/` pipeline, `AGENTS.md` architecture note) and must be fixture-tested per provider, not assumed.

The plan/review's fear of a "browser-originated provider test" is **partially realized differently**: nothing is direct browser→provider, but the connectivity tests and quota reads are **server-originated provider calls that bypass the guarded dispatch path** (no cooldown, no dispatch accounting, no policy) via the `api-call` escape hatch. `docs/management-api-v8.md` does not gate `requests/api-call` behind any additional flag; it is always registered when management is enabled (`server_management_v8.go:31`).

**Mitigation options (proposed, no code yet):**

1. **Operational (no fork):** do not distribute the management key to untrusted users; treat the panel as operator-only. Tests are then explicit operator actions. This satisfies "management usable without inference" but leaves inference-capable buttons one click away.
2. **Patch the dashboard asset (source-available MIT, single HTML file):** build a pinned `management.html` variant that removes/hides the connectivity-test and quota-fetch action buttons (and the `verify` opt-in), keeping login/status/discovery/config. Rebuild from the `v1.27.0` tag; re-verify the digest of our variant. This satisfies "disable bypass actions without a custom UI" — same UI, minimal patch, pinned build.
3. **Harden the server side:** the `requests/api-call` route itself has no allowlist. An upstreamable patch (or plugin `ManagementAPI` shadow route) could disable it. Upstream change is a bigger ask; propose (2) first and file the upstream issue in parallel.

Note the earlier review's claim "runs in the browser" (`README.md:152` troubleshooting note at v1.27.0) is about reachability/CORS of the *target*; the request itself is issued by the backend on the dashboard's initiative and outside the dispatcher. Either way the invariant requirement stands.

## Configuration write/lock/migration summary (backend `v8.0.49`)

- Storage: single YAML file (`server.host/port`, `config-version: 8` layout, `config.example.yaml`). Stores: file default; optional Postgres/git/object-store credential backends (`AGENTS.md` "Storage backends"; `internal/store/`).
- Write paths: v0 per-field endpoints (immediate, no precondition) and v0 `PUT /v0/management/config.yaml`; v1: `/v8/management/config*` with `If-Match` (ETag = SHA-256 of disk bytes) and full validation (`ValidateV8Config` rejects unknown sections and legacy keys — `internal/config/config_v8.go:887-925`).
- Migration: legacy → v8 layout happens only on a successful v8 write; reads and rejected writes never migrate (`docs/management-api-v8.md:24-26`; code comment `config_v8.go:20-21`).
- Hot reload: after save, an ordered async reload applies the new config in-process (`handler.go:247-294`); a separate file watcher reloads out-of-band edits (`internal/watcher/`, `sdk/cliproxy/service_lifecycle.go:198-226`). Restart-required settings are documented per field (e.g. `trusted-proxies` — `internal/config/config.go:31-33`).
- **Gap for the plan's "revisioned writes with conflict rejection":** `If-Match` exists and is correct, but nothing requires writers to use it. T3-hub-side write behavior is unknown (milestone 3). Do not invent a new control plane; constrain writers and use `If-Match` (`gateway-product-scope-refactor.md:54`).
